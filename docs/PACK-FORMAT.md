# PGM 封包格式 / Pack format

记录 PGM 的 `gmcode.bin`（脚本）与 `gmdata.bin`（图片）两种封包的逆向结果。

**状态**

| 部分 | 状态 |
|---|---|
| `gmdata.bin` 容器结构 | ✅ 完全解出，可直接读 |
| `gmcode.bin` 容器结构（目录、文件名、偏移、大小） | ✅ 完全解出 |
| `gmcode.bin` 载荷 | ✅ **已破解**（按行 + 64 字节周期 XOR），解出文本 99.8% 正确 |
| 剩余 0.2% 异常字节 | ✅ 已解决（打包器的 anti-NUL 规则，见 4.7） |

正是这个阻塞点让宿主暂时走"明文 `src/` 目录"模式（见 `src/pgm_pack.c`）。

---

## 1. 尾部结构（两个封包共有）

封包末尾是"目录 + 尾部信息"，且**文件名是明文**（不是加密的，这曾经让我
们走了弯路 —— 早期误以为整个文件都被加密）。

### gmdata.bin

```
[数据区 0 .. dir_start)        每个条目的内容按目录里的 offset/size 取
[目录区]                         N 条 × 124 字节
[尾部信息]                       88 字节
```

目录项（124 字节）：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0 | u32 | 数据在文件中的偏移 |
| +4 | u32 | 数据长度 |
| +8 | char[116] | 文件名，NUL 填充。**GBK 编码**，中文文件名原样存放 |

实测：62 条，目录起于 `0x34014e`，尾部 88 字节为
`{u32 dataEnd, u32 ?, u32 ver=1, u32 nums=63, u32 0, char info[]}`，
其中 `info` 是打包工具的参数字符串 —— 本例是 `"res files"`
（对应 `pack.bat` 里的 `pgrp -o ../src/files "res files"`）。

### gmcode.bin

同一套思路，但目录项是 **128 字节**：

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0 | u32 | 保留（全 0） |
| +4 | u32 | 未知（疑似行数/块数） |
| +8 | u32 | 数据偏移 |
| +12 | u32 | 数据长度 |
| +16 | char[112] | 文件名，明文 GBK |

实测：43 条，目录起于 `0x43a3f`，43×128 + 96 = 5600 = 文件尾 - 0x43a3f ✓

偏移链首尾闭合（可以直接验证结构正确）：

```
条目 1  ce_init.lua    off=0        size=572     → 0 .. 572
条目 2  CGlist.lua     off=572      size=6496    → 572 .. 7068
条目 3  KeySetting.lua off=7068     size=212     → 7068 .. 7280
...
条目 42 first.ev       off=265680   size=11086   → 276766  ← 正好等于尾部的 dataEnd
```

43 个文件名也与 CE + 原版 v0.83 两套框架合起来完全对得上（`lg_init.lua`、
`ce_init.lua`、`TextLayer.lua`、`screen_rect.lua` … 都在）。

## 2. 条目载荷：未解的部分

假设目录给出的 `(offset, size)` 是对的，那么每个条目的载荷开头长这样：

```
ce_init.lua   (off=0,      size=572):
  0b 00 00 00 | 1f 77 7c 37 35 37 10 5f 14 5e 1e | 46 00 00 00 | 1f 77 7c 64 6d 7d ...

CGlist.lua    (off=572,    size=6496):
  0b 00 00 00 | 1f 77 7c 37 35 37 10 5f 14 5e 1e | 43 00 00 00 | 1f 77 7c 64 6d 7d ...

KeySetting.lua(off=7068,   size=212):
  0b 00 00 00 | 71 1d 03 15 19 13 64 13 40 10 7b | 09 00 00 00 | 3b 77 71 79 ...

lg_init.lua   (off=126578, size=13209):
  11 00 00 00 | 1f 77 7c 76 7f 6f 1f 1c 52 1f 54 57 51 4b 1f 1c 52 | 0f 00 00 00 | ...
```

### 已排除的假设

* **不是整体 XOR 加密**：长度字段是干净的 `u32`，如果整文件加密它们不会是 11/70 这种值。
* **不是单纯压缩**：`ce_init.lua` 明文 5931 字节、载荷 572 字节（约 10×），
  但 `CGlist.lua` 明文 186 字节、载荷却有 6496 字节（35× 膨胀）。压缩不可能既压又涨。
* **`[u32 len][len 字节]` 的 len 不是文件名长度**：`0b 00 00 00`（11）后面
  11 字节，在 `ce_init.lua` 和 `CGlist.lua` 两个不同文件的载荷里**完全相同**。
  同一个"名字"不可能是两个不同文件。
* **不是 Lua 5.1 字节码**：Lua 字节码头是 `1b 4c 75 61`（`\x1bLua`），这里没有。
* **不是 zlib/deflate**：`0x1f` 作为 deflate 首字节是 `BFINAL=1, BTYPE=11`（非法）。

### 下一步的确定路径

不再靠猜，直接读 `pgsp.exe` / `pgrp.exe` 的实现。两条可行路线：

1. **反汇编 ARM 版** —— `tools/PGMv0.83主引擎文件/ANDROID/PGMv0.8beta5.apk`
   里的 `libnge2app-jni.so` 含封包读取代码，ELF/ARM 比 x86 好读，符号表部分保留
   （已确认能 `nm -D` 出 `NGE2_GetTicks` 等符号）。
2. **差分实验** —— 用同一份明文源，构造不同内容再打包，比对输出。但没有可用的
   `pgsp.exe` 运行环境（本机无 Wine，Homebrew 又因 `/opt/homebrew` 属 root 装不了）。
   若之后修好 Homebrew，`brew install --cask wine-stable` 后即可做差分，
   这是最快能确定算法的方法。

### 另一个线索：`PGD_*` 操作码

《PGM指令表v0.7.md》里有一组 `PGD_*` 常量：

```
PGD_UNKNOWN, PGD_SINT8, PGD_UINT8, PGD_CODE, PGD_NEWLINE,
PGD_TABLE, PGD_COLOR, PGD_DCOLOR, PGD_DELAY, PGD_WAITKEY
```

这是**事件脚本（.ev）的二进制操作码**。所以 `.ev` 文件在打包时会被编译成操作码
序列 —— 这解释了为什么载荷不是明文 Lua。而 `.lua` 是否同样被编译，还需要验证。

## 3. 当前替代方案

在载荷解码完成之前，宿主用明文目录模式（`PGM_PACK_DIR`）：
`PackCreate("data/gmcode.bin")` 检测到是二进制封包后，转而从游戏的 `src/`
目录按文件名查找脚本。这样可以在不碰封包的前提下继续验证 Lua 宿主与 API。

`pgm_pack_open()` 里有一个 `looks_binary_pack()` 负责识别，将来补上解码后
只需在 `pgm_pack_read()` 里加 `PGM_PACK_BIN` 分支即可，上层无需改动。

## 4. 载荷已破解

### 4.1 结构

每个文件的数据区是一串记录：

```
[u32 长度][长度个字节] [u32 长度][长度个字节] ...
```

每条记录 = 明文源码的**一行**（不含换行符）。重建文件时用 `\r\n` 连接。

### 4.2 加密

```
plain[i] = cipher[i] ^ KEY[i % 64]
```

**64 字节固定密钥流，索引是「记录内偏移」，每条记录从 KEY[0] 重新开始。**
密钥是打包工具内置的常量，由 `pgsp` 在运行期生成（在 `pgsp.exe` / `pgrp.exe` /
`win32main.exe` / PSP `BOOT.BIN` 里都搜不到这 64 字节的明文常量）。

```
KEY = 32 5a 5c 59 50 40 30 33 7d 30 7b 78 7e 64 30 33
      7d 50 57 45 5a 57 45 5a 57 41 57 54 7e 64 59 50
      5c 4d 50 40 50 53 49 30 7b 78 7e 7b 30 33 59 5e
      65 7b 5a 57 46 51 49 7b 69 48 46 51 6f 64 54 32
```

### 4.3 怎么破出来的

1. 观察到载荷里有大量**重复的密文片段**（`;SUP5.T`、`;?2=`、`;S974` 各出现几十次）
   → 说明是替换类变换，相同明文产生相同密文。
2. 记录长度分布与源码的行长分布高度吻合（3=`end`、4=`\tend`、5=`\t\tend`…）
   → 确认记录是"行"，且**长度字段是明文**。
3. 用最高频的几条行做已知明文对：
   ```
   W48        -> end
   ;?2=       -> \tend
   ;?0*5      -> \telse
   ;S974      -> \t\tend
   ;S95#%     -> \t\telse
   ;SU<>$     -> \t\t\tend
   ```
   解出 `KEY[0..4] = 32 5a 5c 59 50`。
4. 67 字符的注释行 `-- ` + 64 个 `=` 一次把 KEY 拉到 66 字节。
5. **发现周期 64**：70 字节版本的同一条注释行给出 `KEY[64..66] == KEY[0..2]`、
   `KEY[67..69] == KEY[3..5]`。三个独立位置同时吻合的概率约 1.6e-8，故周期为 64 确定无疑。
6. 解密验证：`-- new line`、`GAME_NAME = "PGMCE"`、`MSGNAME_NUM = 32`、
   `speakmode(speak_mode_sample)`、`pmplay("system/test.pmp")` 等全部正确还原，
   中文 GBK 注释也正常。

### 4.4 目录的一个坑：字段错位一格

目录里第 *i* 个**名字**的 `offset/size` 字段，实际写在**第 i+1 条记录的头部**。
也就是说每个文件的内容紧挨在"下一个"名字之前：

```
名字 CGlist.lua     的字段区间里装的是 ce_init.lua 的内容
名字 KeySetting.lua 的字段区间里装的是 CGlist.lua 的内容
```

按名字逐文件比对相似度即可确认（错位时每个文件都匹配到"别人"，修正后每个文件都匹配到自己）。
最后一条名字（`first.ev`）的字段缺失，其数据落在数据区末尾、目录之前的那一小段，
用"未被认领的区间"补上。

### 4.5 打包器的 anti-NUL 规则（最后一块拼图）

剩下 1016/10027 条记录各有一个字节被解成 `0x00`。定位过程：

1. 统计异常位置的**密文字节**分布，发现它们恰好全部等于 `KEY` 表里的值
   （`0x64` 366 次、`0x78` 152 次、`0x30` 125 次 …… 与 KEY 的取值集合完全重合）。
2. 密文 == KEY 意味着 `plain = cipher ^ KEY = 0`。也就是说打包器的输入里
   **真的写了 0x00**。
3. 反推"0 位置上原本应该是什么字符"，得到的分布又是 `'d' 342 次、'x' 140 次、
   '0' 103 次 …` —— **同样等于 KEY 的取值**。
4. 于是真相是：这些位置满足 `plain == KEY[i]`，XOR 后会得到 0x00。
   打包器为了避免密文里出现 0x00（某处把缓冲区当 C 字符串用，遇到 0 会截断），
   **把这种情况下的字节原样写出**，于是密文 == plain == KEY。

**解包规则**：

```c
p = c ^ KEY[i % 64];
if (p == 0 && c == KEY[i % 64])   /* anti-NUL：还原被打包器换掉的原字节 */
    p = KEY[i % 64];
```

加上这一条后，不可打印字节从 1016 降到 **13**（后者是 GBK 编码边界情况），
`gmcode.bin` 解出的 40 个 `.lua` 文件**全部通过真 Lua 5.1 的语法检查（0 失败）**。

### 4.6 资源包 gmdata.bin

同一套容器，但布局不同，且**载荷不加密**：

| | gmcode.bin（脚本包） | gmdata.bin（资源包） |
|---|---|---|
| 目录项步长 | 128 | 124 |
| 字段偏移 | `offset@+8, size@+12` | `offset@+0, size@+4` |
| 名字偏移 | +16 | +8 |
| 载荷 | 按行 + XOR | 整文件原样 |
| 目录字段错位 | 有（错位一格） | 无 |

`gmdata.bin` 的第一个条目就是一张完整的 PNG（文件偏移 0 处即 `\x89PNG`），
可直接验证映射正确：62 条里有 61 条的头部是 PNG 签名，剩一条是 RIFF。

### 4.7 目录条目数的判定

对 1016 条异常记录做了统计：

* 只有 **11.1%** 的异常字节位于行末 → 不是"行尾特殊处理"。
* 异常集中在少数偏移上（`33` 52 次、`14` 40 次、`13` 25 次、`9` 17 次、
  `29` 14 次 …），但同一偏移在不同记录里都需要**不同的密钥字节**。

最典型的对照（两条记录前缀完全相同，都是 `_D? = ` 结构）：

```
FG_RIGHT_DX = 120   cipher[...] 01 01 4d   → 偏移14: 0x01 ^ 0x30 = '1' ✓  (key 0x30)
FG_RIGHT_DY = 0     cipher[...] 30         → 偏移14: 0x30 ^ 0x30 = 0x00 ✗ (需要 key 0x00)
```

也就是说，若要正确解出后者，文件里该字节应该是 `0x00`，实际是 `0x30`。
这指向"密钥流在少数位置有额外推进"或"打包器对个别字节做了替换"，
必须读 `pgsp.exe` 的写记录循环才能定论。
